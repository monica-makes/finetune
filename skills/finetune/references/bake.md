# Bake

Everything a bake needs: the tuner checklist, the changes list's format, and where each of its lines goes in the code. Read the part for the job.

## Bake a tuner

She pastes the tuner panel's Copy JSON (raw values: numbers stay numbers, toggles stay `true` or `false`, no units; the formats are in `tuner-api.md`).

1. Get the tuner's Copy JSON.
2. Find the `finetune()` call with that `id`.
3. For each key, find where the committed value lives: the custom property's declaration in the stylesheet (usually `:root`), or the config value. For a key without `--`, wherever that value is used (markup, config, a script constant).
4. Write the new value in that file's format. `range`: add the control's `unit`. `toggle`: write `on` or `off`. Skip values that already match.
5. A key with no committed home: don't invent one. List it and ask.
6. Remove the `finetune()` call, any code that only fed it, and the script tag that loads `finetune.js` unless another `finetune()` call on the page still uses it.
7. List every file and line touched.
8. Ask before committing.

## The changes list

She pastes what the toolbar's Copy changes button copied, with nothing else to say: the paste is the ask. It looks like:

```
Bake these finetune changes into the code with the finetune skill:
finetune changes · /Users/you/Projects/finetune/demos/index.html · 1440×900
page                 background: #1E1E1E
h1                   font-size: 44px; letter-spacing: -0.014em
p.eyebrow            text: Meta · Redesign 2
div.card             row-gap: 12px; padding-top: 16px; padding-bottom: 16px; align-items: center
group 1              div.hl-place, div.hl-bio
group 1 auto layout  display: flex; flex-direction: column; row-gap: 8px; justify-content: flex-start; align-items: flex-start; width: fit-content
```

The first line asks for the bake. The header line under it (`finetune changes · …`) names the page that was edited, by the path in its address bar: a file path for a page opened from disk, or a route (`/home_layout`) for a served app, whose page is the file that renders that route. Without that header line, ask which page it is. After the path come the window's width and height when she copied (`1440×900`; the width is the one media queries saw, so it tells you which breakpoint the edits were seen at), then the page's theme (`dark`, `light`, or a `data-theme`'s own name) when finetune found a switch for one. No theme part means finetune found no switch, not that the page has none (lovable-classic's Tailwind v3 `.dark` block copies none in light): before writing a colour, still check the code for `.dark`, `[data-theme]`, `dark:` or `prefers-color-scheme`, and keep its other themes as "Theme and dark mode" says. Each line after it is a selector, then what changed on that element: CSS declarations, and `text:` for words retyped in place (it's the element's new inner HTML, on one line, where Enter typed a `<br>`: the source's line breaks and indents are one space, as the browser shows them, except in an element that keeps white space, like `white-space: pre`, where a line break is written `\n`; Copy adds no quotes, so any quotes are her words). A line lists only what changed, never what the code already has. The lines come in this order, not the page's: `page`, then `component` lines, then each element in the order she first edited it (with the notes under it), then groups, keyframes and `animate()` lines. `page` is the page fill, written as one CSS `background`, or as `background-image` when her fills sit over the code's own background (see that note below). `page (main.app)` means a full-page wrapper paints the page, so the fill is that element's background, not the body's.

Where the page's development build records where each element is written (React's dev source, Lovable's `data-lov-id`, TanStack's `data-tsd-source`), the first column of a line ends with ` @ file:line[:col]`, a path from the project's root: the file to open for that line. A production build or a page with no such record has no `@`; find the element from its selector. What the `@` names depends on the line:

- `h1.font-display @ src/components/Hero.tsx:15:10`: where that element is written (on a `delete` or `ungroup` line too).
- `component Button (button.inline-flex, 7 on the page) @ src/components/ui/button.tsx:42:12`: the component's own file, where it writes the element it returns. That's where a component edit goes. When the component returns another component (FeatureCard returns `<Card>`), it's that line in the component's own file, not the inner component's: an edit there changes this component's instances only.
- `component Button variant=outline (button.inline-flex, 3 on the page; sizes lg, default) @ src/components/ui/button.tsx:42:12`: an edit to the instances given that `variant`, read as the code's cva variant. An instance given no variant reads `default` when another instance passes `default` by name, else `(none)` (see "Components"). `sizes` (or `intents`, `tones`) lists what those instances are given, for the bake only: the edit isn't split by it.
- `component Card (div.rounded-lg, 7 on the page; 3 inside FeatureCard) @ src/components/ui/card.tsx:6:3`: 3 of the 7 are rendered by FeatureCard, which returns a `<Card>`. They're Card's too, so they changed on the page with the other 4, and the edit to card.tsx changes them in the code.
- `button.inline-flex (this Button only) @ src/components/Navbar.tsx:28:12`: where that one instance is used.
- `div.flex (this CardHeader only) @ src/components/FeatureCard.tsx:13:6, inside this FeatureCard at src/components/Features.tsx:20:12`: the instance is used inside another component that's on the page more than once, so its line is shared by every one of those. Write the change at the second place, into what that one outer instance is given (a prop, or a modifier it passes on), not at the first place, which would change them all. Ask if the outer component has no way to pass it on yet.
- `span.text-4xl (inside this CardContent only) @ src/components/Pricing.tsx:30:18, this one at src/components/Pricing.tsx:28:14`: the element is written at the first place; the instance it sits in is used at the second.
- The parts always come in this order: the selector, `(this X only)` or `(inside this X only)`, the `(item ...)` part below, ` @ ` the first place, then `, inside this X at` or `, this one at` the second: `div.flex (this CardHeader only) (item "Instant capture", 1 of 3) @ src/components/FeatureCard.tsx:13:6, inside this FeatureCard at src/components/Features.tsx:20:12`.

The records the `@` comes from (`data-lov-*`, `data-component-*`, `data-tsd-source`, React's `__source`) are added by the dev build, not written in the source: never write or update them.

The line and column point at the element's opening tag. The column can be off by one between builds; the line is what counts. An `@` with a file and no line (`@ src/components/Hero.tsx`) comes from React 19, which records where an element was made only as a browser stack, whose line numbers are the dev server's compiled code, not the file's: open that file and find the element in it by its selector and its words.

A line for an element inside one item of a React list (a `.map()`) carries ` (item "Team", 2 of 3)` before its `@`: that item's React `key`, then its place among the list's items. The JSX the `@` points at is shared by every item, so write the change for that item only: in its entry in the data (the plan whose key is `Team`), or as a condition on that key, never into the shared JSX. Ask if the data has no field to carry it. One exception: when Copy has a line for every item of the list (`1 of 3`, `2 of 3` and `3 of 3`) with the same change, she made it on all of them, so write it once at the line's first `@` place, the shared JSX, where it reaches every item as she saw. If that place is in a component's own file (FeatureCard.tsx) and the component is used anywhere else (search `src/` for its imports), the change would reach those too: list them and ask.

A line's selector names the element as it was when she copied. An edit made before the page changed (a section added above it, a list item moved) stays with the element it was made on, found again by where the code writes it, its list key or its words, and its line names that element by its selector now. A group's line and a scale note name it the same way.

Comment lines (`/* ... */`) carry notes for the line above them (a `not found` note comes before its line, or stands alone):

- `/* page (div.min-h-screen): under these layers is the code's own background (#09090B in dark); keep the code's */`: her page fill is layers added over the page's own fill, which she never changed (the colour in brackets is how it read then, in that theme). The `background-image` line above it is her layers only. Keep the code's own background exactly as it is (its token, class or rule, in every theme) and add her layers as a `background-image` on the same element (a `bg-[linear-gradient(...)]` class, or the rule that sets its background). Never write the colour in brackets: it is one theme's value of the code's token.
- `/* h1.font-display: changed at 390px wide */`, `/* h1.mt-6: changed in light */`, or both: that line's edits were made at another window width or theme than the header's. They were seen there, so write them for that breakpoint or theme (or ask), not for every one. `/* h1: rotate changed at 390px wide */` names the properties when only some of the line's were: write those for that breakpoint and the rest as usual. A theme is only named for a value that carries colour (a colour, a background, a border, a shadow, a colour filter, a custom property, the page fill); every other value holds in every theme.
- `/* div.p-6:nth-of-type(3) > span.text-4xl: not found, the page changed since this edit (was "Team") */`: the element the edit was made on isn't on the page as it was (the key, words or file in brackets are how it was known). Followed by its lines commented out (`/* div.p-6:nth-of-type(3) > span.text-4xl  opacity: 0.4 */`), the selector now finds another element (another list key, another file or tag): the edit didn't show on the page, so don't bake it onto what the selector finds; list it and ask which element she meant, then bake those values onto the element she names. With the edit's own line after it, nothing on the page matches the selector at all (the element may just not be showing, like a closed menu): bake the line as usual, finding the element in the code by its file and words.
- `/* h1: its words were "Tableware made slowly, for every day." when this edit was made; check it is the same element */`: the edit is on the element its selector finds, the same tag from the same file, but that element's words differ from when she made it. Usually the page changes them itself (a count-up, a rotating word, a price toggle) and the line is right: bake it as usual. If the code's words for that element are another element's entirely, ask before baking.
- `/* h1.hero-title: these words are built in code (the page rewrote them); change the expression, ask first */`: after she retyped the words, the page's code wrote them again (`{"Count " + n}` in JSX, a script setting the text). Her `text:` is what she wants to read there, not words to paste over the expression: show her the expression and ask how to change it (another string in it, another value in the data).
- `/* p.mixed: these words are built in code from several parts, so the page doesn't show this edit; change the expression, ask first */`: the words are JSX made of parts (`Plan {name} pricing`); React keeps its own hold on each part, so finetune didn't put her words on the page (an edit saved before it refused to retype such words). Treat it as the note above: ask before changing the expression.
- `/* h1.hero-name: text style .b1 (defined in code) */`: she picked the class `.b1` from Typography's Text styles, and the line above still has every value it gave. Add the class; don't write those values (see "Styles defined in code").
- `/* div.span-7: columns 3-5 of 12 (.wrap.grid), full span, at 1440px wide */`: an Align to columns (`aligned left`, `centered`, `aligned right`) or Make selected N cols wide (`full span`) put the layer on those columns of the page's grid, the element named in brackets, at that width. The layer is one of that grid's items, so place it with the grid rather than writing the px its line carries, and write it in the rule or variant active at that width (the `@media` or `lg:` where the grid has that many columns), not the base rule, unless the grid has that many at every width. Columns `a-b` are the ones she picked, `n` of them (`n = b - a + 1`); each kind reads:
  - `full span`: `grid-column: a / span n` (or the grid's own span and start classes). The layer fills those columns, so also drop the `justify-self: start` its line carries: the resize wrote it to let go of the grid's stretch, and kept it would shrink the layer to its content.
  - `aligned left`: `grid-column: a / span n` with `justify-self: start`. The layer keeps its own width, so write the width it has on screen if the code doesn't set one (`justify-self` stops the stretch).
  - `centered`: the same with `justify-self: center`.
  - `aligned right`: the same with `justify-self: end`.
  - Then drop the `translate` and px `width` its line carries for that placement.
  - `, fluid columns`: the grid's column count comes from its own width (`repeat(auto-fit, ...)` or `auto-fill`), so no rule or variant holds that count. A `grid-column` would land on other columns, or add a track, at other widths: write the px as they come, or ask.
  - `, before its column 3 so the grid moves it to the next row`: the layer's own cell is column 3 of its row, and the preview only moved it within that row. A `grid-column` starting earlier makes the grid's auto-placement put it on a new row and leave its cell empty, which isn't what she saw. Say so and ask: reorder the items in the code (or place them with `grid-row` or `order`), or keep the px.

  On a page whose grid is its content column (no full-width grid: a `.container` or `mx-auto max-w-7xl px-6` with section grids inside), the brackets name the container, then the grid inside it whose tracks the columns are, as one selector: `(.mx-auto.max-w-7xl.px-6 .grid.gap-6.md\:grid-cols-3)`. Several section grids share those columns when they're joined with commas (`.container .features-grid, .container .pricing-grid`): place the layer in the one that holds it, the same way. The column count is that grid's (often 2 or 3), at that width.

  `(.wrap.grid, not its item)` means the layer sits on those columns but isn't one of that grid's items (it's inside something else, like a two-column `.split`): a `grid-column` on it would land in whatever grid holds it, so write the px as they come, or ask. `(guide 8 col · 20 gutter · 200 margin)` means her own guide, not a grid in the code: write the px as they come, or ask. The note only shows while the layer still sits where the columns put it; a move since then drops it. The layers of a `group N` moved or sized as one unit, so each fills only its part of the columns and carries no note, unless one of them sits on the columns by itself.

## Bake the changes list

1. Open the page named on the header line and the stylesheets it uses. A route is the file the app's router renders for it:
   - React Router (Lovable's Vite apps): the `<Route path="/pricing" element={<Pricing />} />` in `src/App.tsx`, then the file `Pricing` is imported from (usually `src/pages/Pricing.tsx`; `/` is often `src/pages/Index.tsx`).
   - Next: `app/pricing/page.tsx` (`/` is `app/page.tsx`, often under `src/`); a folder in brackets, `(marketing)`, isn't part of the route. The older `pages/pricing.tsx` maps the same way.
   - TanStack Start or Router: `src/routes/pricing.tsx` (`/` is `src/routes/index.tsx`); a dot in a file name is a `/` (`blog.post.tsx` is `/blog/post`).
   - A line with an `@` names its own file: open that one for that line. That `@` is Copy's; an import written `@/components/...` is the project's alias for its `src/` folder (`paths` in `tsconfig.json`, or the Vite config), unrelated to it.
   - With no `@`, find the element from its selector. Search the page's components for its classes as the code writes them in a `className`: a selector escapes Tailwind's characters, so `md\:grid-cols-3` is `md:grid-cols-3` in the code, `w-\[18px\]` is `w-[18px]`, `w-1\/2` is `w-1/2`. Where several elements match, the `:nth-of-type(n)` steps and the words pick one; still more than one, ask.
2. For each declaration, find where that property's committed value lives for that element (on a Tailwind project, its `className`: see "Tailwind projects" below): a custom property it reads that belongs to this page (declared in the page's own stylesheet, or a tuner's `--` key: `font-size: var(--hero-size)` means write `--hero-size`), else the rule that sets it, else add it to the rule that best matches the selector. With no such rule, add one where the page keeps its CSS (its stylesheet, a `<style>` in the page, or inline `style` if that's all the page uses). For `page`, the `body` background, or the named wrapper's.
   - A selector with `:nth-of-type()` names one of several siblings with the same tag and class (cards in a list, items from a loop), and the edit showed on that one only. Don't write it into the rule they all share: write it where that one is made (its data, or a modifier class or style on it), or ask.
   - Never redefine a shared design token (declared in the project's global stylesheet, read across pages). That changes every page. Point this element at another token instead, or ask.
   - A value that is a `var(--x)` (`color: var(--text-primary)`) is a token she picked from Color styles: write that token, never the value it resolves to, and never redefine it (see "Styles defined in code"). There's nothing to compare.
   - Tokens first, always. Before writing a value, load what the project names: Tailwind v3's `tailwind.config.*` (the default scale plus `theme.extend`; shadcn's colours are `hsl(var(--primary))` over bare triples in `:root` and `.dark`, and `--radius` sets `rounded-lg`, `-md`, `-sm`), Tailwind v4's `@theme` / `@theme inline` blocks (and `--spacing`, the step every `p-*`, `gap-*`, `w-*` multiplies), or a plain page's `:root` and `[data-theme]` custom properties. Then write the token whose value on that element is the line's value, as a utility (`bg-primary`, `gap-6`, `rounded-lg`) or a `var()`. Check what it resolves to there, theme included, not just its declaration.
     - Colours: compare as 8-bit sRGB. Convert the token (an HSL triple, `hsl()`, `oklch()`) to hex before comparing it with Copy's `#RRGGBB`: lovable-tanstack's `oklch(0.55 0.15 200)` is `#008994`. Copy writes a colour with alpha as `rgba(r, g, b, a)`: that's a token with an opacity modifier, `/` and the alpha in percent. `rgba(102, 68, 238, 0.1)` over a `--primary` of `#6644EE` is `bg-primary/10` (shadcn's `hsl(var(--x))` takes the modifier on v3 too); in plain CSS, `color-mix(in srgb, var(--primary) 10%, transparent)` or the form the project already uses.
     - Spacing, radius and font size: compare in px against the project's own scale (`--radius: 0.5rem` makes shadcn's `rounded-md` 6px; `pl-5` is 20px on v3, and on v4 at its default `--spacing` of 4px).
     - No token matches: write the value as it comes (an arbitrary value, `gap-[18px]`, in Tailwind; a literal in plain CSS) and name it in the list of touched lines, so she sees where the code leaves its scale. If the project's rules say a kind of value must come from tokens (colours often do), list the line and ask instead, naming the nearest tokens and what each resolves to on that element. A step only v4 has (`gap-4.5`, any multiple of `--spacing`) does nothing on v3, which knows only its scale's steps: write `gap-[18px]` there.
   - The header's width says which breakpoint showed her edits (a line's `changed at Npx wide` note gives its own). Write each value where it applies at that width: in plain CSS, the rule in the `@media` that applies there; in Tailwind, the utility whose variant is active there (by default `sm:` 640, `md:` 768, `lg:` 1024, `xl:` 1280, `2xl:` 1536; the config or `@theme`'s `--breakpoint-*` can move them; `@md:` and the like follow a container's width, not the window's). At 1440, a `text-3xl md:text-4xl` heading shows `md:text-4xl`, so her 40px is `md:text-[40px]` (with its line-height, see "Tailwind projects"); changing the base `text-3xl` does nothing at that width. Say which breakpoints you left as they were, and ask whether they follow. A base utility with no variant over it (`gap-6` beside `md:grid-cols-2`) shows at every width, so changing it changes them all: say so.
   - A value the code computes from the window (`clamp()`, `vw`, `%`, a fluid token like `--step-4: clamp(...)`) is not replaced by px: the px is right at that width only (claude-static's `h1 { font-size: var(--step-4) }` is 88px at 1440 and 47.56px at 390). Change the bound in play at that width (at the widest, usually the clamp's maximum) and keep it fluid, or ask. If the clamp is a shared token, give this element its own clamp rather than redefining the token.
   - A px `width` / `height` that Copy wrote for a layer because it filled its parent (a child that followed a resize, a `group N <selector>` line), where the code makes it fill (`w-full`, a flex or grid stretch), is right at this width only: say that the px makes it fixed at every width and ask before writing it.
   - `translate: X Y` is a move, measured from where the code places the element before any translate, and it's the element's whole translate: a CSS `translate` the code already gives it (Tailwind v4's `translate-x-*` / `translate-y-*` included) is in X and Y (finetune took it over before moving it), so it replaces the code's (`translate: none` takes the code's off). Tailwind v3's `translate-*`, `rotate-*` and `scale-*` set `transform` instead, which finetune never takes over: there Copy's value is her change on top of the code's utility, not the whole value (see "Moves on Tailwind v3"). What it took over is the element's resting translate, never one a `:hover` rule adds (`hover:-translate-y-1`, `group-hover:`): keep those hover variants and rules. The same holds for a `rotate` or `scale` line (on v3, see "Moves on Tailwind v3"). But a hover that sets the same property, or the same Tailwind variable, replaces her value while it's hovered: Tailwind's `hover:-translate-y-1` sets only the Y, `hover:scale-105` both scales, `hover:rotate-6` the whole turn. So write her value so the hover state still carries it. In Tailwind, write the move as `translate-x-*` / `translate-y-*` (on v3 those are a `transform` finetune never took over: see "Moves on Tailwind v3"), and where her line moves along an axis the hover sets, write that hover as her value plus the hover's (Y 12 under `hover:-translate-y-1` is `translate-y-[12px] hover:translate-y-[8px]`); with Y 0 under a Y-only hover, write `translate-x-*` alone and keep the hover as it is. A flip or turn under a hover scale or rotate gets the combined hover value (`-scale-x-100` under `hover:scale-105` is `hover:-scale-x-105 hover:scale-y-105`; `rotate-90` under `hover:rotate-6` is `hover:rotate-[96deg]`). In plain CSS whose `:hover` rule sets `translate`, `rotate` or `scale` itself, write the combined value in a `:hover` rule for this element (its translate 40px 12px under a hover of `0 -4px` is `40px 8px` on hover). Never write an arbitrary `[translate:...]`, `[rotate:...]` or `[scale:...]`, or an inline style, for a property a hover sets: the arbitrary one drops her X on hover in Tailwind v4, and an inline style overrides the hover. Where the hover can't be combined this way, ask. X or Y can keep a `%` the code had, with her px in a `calc()` (`calc(-50% + 12px)`): keep that as written. If the element is placed with `left` / `top` (or custom properties feeding them) and X and Y are plain px, add X to its left and Y to its top there, take off a translate finetune took over (a CSS `translate`, or Tailwind v4's `translate-x-*` / `translate-y-*`), and write no translate. On Tailwind v3 the code's `translate-x-*` / `translate-y-*` are not in X and Y, so they stay: `absolute left-1/2 -translate-x-1/2` moved 12px is `left-[calc(50%+12px)] -translate-x-1/2` (taking the utility off lands it half its width off; see "Moves on Tailwind v3"). Other numbers that restate the current position (an old tuner's values, notes) are the starting point, not a conflict. Otherwise keep the translate. A layer in a `group N auto layout` never carries a move in Copy: the group's layout places it (only `translate: none`, where the code's own translate has to come off). A `position: absolute` with `left` / `top` on a child of a flex container is Ignore auto layout; fold any `translate` it also has into that `left` / `top`.
   - `display: inline-block` came with a move, rotate, flip or resize of inline text, which ignores those otherwise. Keep it if any of them stays in the code.
3. Bake every other kind of line as its part of "Line by line" below says, in the order Copy lists them (each layer's own line comes before its group's).
4. A line you can't place with confidence: don't guess. List it and ask.
5. Don't touch `finetune()` calls or the script tag; the inspector stays until she asks to remove it. One exception: a value baked into a tuner's `--` key (step 2) also goes into that control's `value` in its `finetune()` call, since the tuner writes its value inline on the page on every load, over the stylesheet.
6. List every file and line touched, then tell her to press Reset (in the left toolbar, under Save) so the page shows the baked code, not the saved edits. If a tuner's `value` changed, also tell her to press that tuner panel's Reset, so its saved value gives way to the new one.
7. Ask before committing. Do not commit until she says yes.

## Tailwind projects

Most vibecoded apps style elements with Tailwind utilities in their markup, not CSS rules. A project is on Tailwind when it has a `tailwind.config.*`, or a stylesheet with `@tailwind base` (v3) or `@import "tailwindcss"` and `@theme` (v4); `tailwindcss` in `package.json` gives the version. Lovable's Vite apps are v3; its TanStack Start apps and create-next-app are v4; Codex's Vite apps can be either. A plain CSS site (one HTML file with a `<style>` and `:root` tokens, Codex's vanilla `styles.css`) keeps the rule-based route of step 2.

**Where.** Write each declaration as utilities in that element's `className`, in the file its `@` names (or the one step 1 found). Never add a CSS rule or an inline `style` for an element the code styles with utilities. A `component X` line goes into the classes the component writes on its element (its cva entry: see "Components"); a `(this X only)` line into the `className` passed where that instance is used; an `(inside this X only)` line into what the outer instance passes on. A `className` built with `cn()`, `clsx` or a template string: change the string that holds the utility, inside its condition when it's in one. A `group N auto layout` element is written with utilities too (`flex flex-col gap-y-2 items-start w-fit`).

**Replace, never append.** For each declaration, take out the utility that sets that property at the same variant and state, then write the new one in its place. Two utilities on one property don't go by their order in the `className`: the one later in Tailwind's stylesheet wins, and v3 and v4 order them differently (`p-6 p-5` is 20px on v3, 24px on v4; `lg:col-start-6 lg:col-start-3` lands on column 3 on v3, 6 on v4). Shorthands count: on a `p-6` box, `padding-left: 20px` makes `py-6 pr-6 pl-5`; on `gap-4`, a new `column-gap: 20px` makes `gap-x-5 gap-y-4`. Leave utilities under other variants (`hover:`, `focus:`, `dark:`, `md:`) as they are unless the line is about that state, theme or width. A `className` merged by tailwind-merge (shadcn's `cn()`) keeps the last of two such utilities, but replace there too, so the code reads as what shows. A `className` passed to a component can't take out the component's own utility (`<CardContent className="p-8 pt-0">` over its `cn("p-6 pt-0", className)`), so it wins only through tailwind-merge: check the project's `cn` (shadcn's `lib/utils.ts` is `twMerge(clsx(inputs))`). Where it only joins strings, the stylesheet order decides as above: ask. One exception: on v3, a `translate`, `rotate` or `scale` line is folded into the code's utility, not swapped for it (see "Moves on Tailwind v3").

**Theme and dark mode.** A line made in dark (the header's `dark`, or a `changed in dark` note) goes into the `dark:` variant or the token's dark block (`.dark { --x: ... }`, `[data-theme=dark]`), never the base value, which is the light theme's; a line made in light goes into the base and keeps the `dark:` one. The one exception is a colour that is a `var(--x)` token from Color styles: it switches with the theme by itself, so it goes in the base whichever theme she was in (see "Styles defined in code"). How `dark:` switches depends on the project: v3's `darkMode: ["class"]` (Lovable) and v4's `@custom-variant dark (&:is(.dark *))` follow a `.dark` class on `html`; v4 with neither follows the system setting (`prefers-color-scheme`, create-next-app's default), where a `.dark` class does nothing.

A colour the code takes from a theme token is that theme's colour only. That's a `page` line when the body or the page's wrapper paints with one (`bg-background`, `@apply bg-background` in `index.css`, `background: var(--background)`), and any colour line (`color`, `background`, a border's or a shadow's colour) on an element whose code value is one (`text-foreground`, `bg-card`, `border-border`, `var(--x)`). Written as a literal (`bg-[#F5F3EE]` on body, `text-[#333333]` in place of `text-foreground`) it paints every theme: on lovable-classic, dark's `#09090B` page turns light, and dark's `#FAFAFA` text turns `#333333` on that dark page. Don't. List what else reads that token (shadcn's inputs and ring offsets read `--background` too) and ask: change the token's value for that theme (everything on it changes with it), or give the element a value for that theme only (`bg-[#F5F3EE] dark:bg-background`, `text-[#333333] dark:text-foreground`; in plain CSS, a rule that only the light theme matches). The tokens rule's "no token matches, write the literal" doesn't apply here. A colour line that is already a `var(--x)` is not a literal: it follows every theme as the code's token does (see "Styles defined in code").

**Moves on Tailwind v3.** v3's `translate-x-*` / `translate-y-*` (`-translate-x-1/2` included) set `transform`, not CSS `translate`, so finetune never took them over: Copy's X and Y are her move alone, on top of them (lovable-classic's `left-1/2 -translate-x-1/2` box moved 12px right copies `translate: 12px 0px`). Keep the code's utility and fold her move into it, as one utility in its place: `-translate-x-1/2` and 12px is `-translate-x-[calc(50%-12px)]`; or into the `left` / `top` (`left-[calc(50%+12px)]`). Never add a second `translate-x-*` beside it: both set `--tw-translate-x`, one wins and the other is lost (`-translate-x-1/2 translate-x-[12px]` lands 48px off on a 96px box). On v4, `translate-x-*` set CSS `translate`, which finetune took over, so X and Y are the whole value (`translate: calc(-50% + 12px) 0px`): put `translate-x-[calc(-50%+12px)]` in place of the code's utility.

v3's `rotate-*` and `scale-*` (`scale-x-*`, `scale-y-*`) set `transform` the same way, so a `rotate` or `scale` line on an element that has one is her change on top of it: Copy writes the turn she added past the code's, and a flip as `scale: -1 1` over the code's scale. Fold it into that one utility, in its place: add the angles (`rotate-6` with `rotate: 84deg` is `rotate-[90deg]`), and multiply the scales axis by axis (`scale-150` with `scale: -1 1` is `-scale-x-150 scale-y-150`). Copy's value alone in place of the code's draws something else (`rotate-[84deg]` turns 84, not her 90; `-scale-x-100` draws a 144px box 96px wide), and a second utility beside the code's sets the same `--tw-rotate` / `--tw-scale-x` variable, so one is lost. On v4, `rotate-*` and `scale-*` set CSS `rotate` / `scale`, which finetune took over, so Copy's is the whole value (`rotate: 90deg`, `scale: -1.5 1.5`): put it in place of the code's utility.

**Font size and its line-height.** A `text-<size>` utility sets `line-height` with the size. Copy's `font-size: 40px` on a `text-4xl` element was seen with `text-4xl`'s line-height still on it: v3's is fixed rem for `text-xs` to `text-4xl` (`2.5rem`, 40px) but `1`, a ratio, for `text-5xl` and up; v4's is a ratio of the size (`--text-4xl--line-height`, 2.5 / 2.25, so 44.44px at 40px). A bare `text-[40px]` sets no line-height, so the element takes the inherited one (60px on the fixtures), or, where the old size was a variant, the base size's (`text-3xl md:text-[40px]` shows 36px on v3, 48px on v4). Unless the line has its own `line-height`, write the one she saw with the size, the one the code's size utility gives as read from the scale, never assumed to be px: v3 `md:text-[40px]/10` (or `md:leading-10`) for a `text-4xl`, `md:text-[56px]/none` (or `md:leading-none`) for a `text-6xl` (its old 60px kept as `/[60px]` puts her 56px text on a 60px line, not the 56px one she saw), v4 `md:text-[40px]/(--text-4xl--line-height)` (a plain `/10` on v4 is 40px, not the 44.44px she saw).

**Grid placement.** A `columns a-b of N` note (see "The changes list") on Tailwind is `col-start-a col-span-n` at the variant whose grid has N columns (`lg:col-start-3 lg:col-span-3` under `grid-cols-1 lg:grid-cols-12`), with `justify-self-start`, `-center` or `-end` for the aligned kinds, in place of the element's own `col-start-*` / `col-span-*` at that variant (appended beside `lg:col-start-6`, a new `lg:col-start-3` loses on v4). On a plain page, use its own helpers where it has them (claude-static's `.span-N` / `.start-N`), else `grid-column`.

## Line by line

### Text

For `text:`, replace that element's words in the HTML. If the words come from script (an `onChange`, a config value), change them there instead. On a React page finetune won't retype words the code builds from several parts (`Plan {name} pricing`; she's told to change those in Claude Code), so a `text:` line there is words the code holds as one piece: a JSX text, a string literal, or a value in the data that `{title}` reads.

In JSX (a `.tsx` or `.jsx` file), the `text:` line is the HTML React rendered. Change only the words:
- An element in it that a component rendered stays that component in the code: `<svg ... class="lucide lucide-check size-4 text-primary">...</svg>` is the `<Check className="size-4 text-primary" />` the JSX already has, and a shadcn child stays its tag. An element the JSX writes itself (`<span class="font-medium">`) stays as it's written there, with its `className`.
- Decode HTML entities into the characters they stand for (`&amp;` is `&`, `&lt;` is `<`, `&nbsp;` a no-break space), and write a `<br>` as `<br />`. In JSX text, `{`, `}`, `<` and `>` go in as `{"{"}` and the like.
- Words that come from props or a data array (`{feature.title}`, a `.map()` over `plans`) change in that data, at the item the line's `(item "Key", i of n)` names (or its `:nth-of-type(n)`: the nth item, unless the array is sorted or filtered before it renders), never in the JSX every item shares.

### Styles defined in code

Typography's Text styles and the text Fill's Color styles list what the page's own CSS defines ("Defined in code"). A pick names the code's own style, so bake the name, never the values behind it.

- **A colour token**: a colour line whose value is `var(--x)` (`color: var(--text-primary)`, `fill:` on SVG text). Write that token the way the project writes colours: on Tailwind, the utility that reads it (`text-accent` from v4's `--color-accent` or v3's `colors.accent`; shadcn's `--primary` is `text-primary`), else `text-[var(--x)]`; in plain CSS, `var(--x)` in the element's rule. Replace the code's colour (its utility, rule or inline `style`), at the breakpoint she saw it at. It switches with the theme by itself, so Copy gives it no `changed in dark` note and it goes in the base value, not `dark:`; but a `dark:` utility or a `.dark` rule on the same property still wins in that theme: say so and ask whether it goes. Never write the colour it resolves to, and never redefine `--x`.
- **A text style**: a `/* <selector>: text style .b1 (defined in code) */` note under a line, or `/* component Name: text style .b1 (defined in code) */` under a component's line (add it where the component renders that element). Add the class (`b1`) to the element's `class` or `className`. The line's declarations that the class gives (the class's own values at the width she saw, as its rules write them) are what it brings: don't write them as literals. Then take off what would beat it on those properties, or the page won't show what she saw: the element's own rule (a stronger selector, or a later rule of the same strength), an inline style on them (a React `style={{ fontSize: 14 }}` prop or a `style` attribute: take those keys out, and the prop if nothing is left), or utilities on the same properties (`text-4xl font-bold`, as "Replace, never append" says). If that rule is shared with other elements, don't edit it: ask. A `text-<size>` you take off also set the line height: when the class gives no `line-height`, keep the one she saw as its own utility, as "Font size and its line-height" says (v3 `leading-10` for a `text-4xl`, v4 `leading-(--text-4xl--line-height)`). A declaration on the line that the class doesn't give is her change on top: bake it as usual, after the class. With a `changed at Npx wide` note on those properties, she saw the style at that width only, and a class in `className` applies at every width: on Tailwind, add it under that breakpoint's variant where the class takes variants (v4 an `@utility`, v3 a class in `@layer components` or `utilities`), and take off what beats it at that variant only; otherwise (a plain CSS class) don't add it at every width or copy its values into a media rule: list the line and ask.

### Groups (`group N`)

`group N  a, b, c` means she grouped those layers (Figma's ⌘G). Wrap them in one new element in the code, a layer of its own, where the first of them sits in the markup, holding them in the order the line lists them (their order in the code); name it for what it holds (ask if unsure). The new layer becomes their parent and their siblings change, so first find the rules that reach them through their parent or siblings (`>`, `+`, `~`, `:nth-child()`, `:nth-of-type()`, `:first-child`, `:last-child`, `:only-child` and the like, or `:has()` on the old parent). After the wrap those stop matching (or match other layers) and the layers lose their look. Re-point each so it matches exactly what it matched before (these layers and their old siblings), or ask. If they're placed with `left` / `top`, the new layer takes their shared top-left and each one's `left` / `top` becomes relative to it, so nothing moves on screen. Bake their own lines (moves, styles) first, then wrap.

On Tailwind, those rules are utilities. On the parent: `space-x-*` / `space-y-*` and `divide-x-*` / `divide-y-*` (they give each child a margin or a border by its place among its siblings: on v3 every child after the first, on the top; on v4 every child but the last, on the bottom), and `*:` or `[&>*]:` variants. On the layers: `first:`, `last:`, `odd:`, `even:`, `only:`, and `group-*:` / `peer-*:`. After the wrap the new element is one child where there were several, so the spacing moves: in a `space-y-4` list of three with the last two wrapped, the third rises 16px. Give the new element what keeps them where they were (`space-y-4` on it too, for the space between the two), or ask.

Layers rendered from one JSX line in a `.map()` (or any loop) are one element in the code: some of them can't be wrapped in place. Say so and ask: split the array (`items.slice(0, 2).map(...)` inside the new element, the rest after it), or add a field the loop groups by. Inside a `ul` / `ol`, a `table` or a `dl`, a `div` around `li`, `tr` or `dt` / `dd` elements is invalid markup: wrap them in what keeps it valid (an `li` holding a nested `ul`), or ask.

### A group's auto layout (`group N auto layout`)

`group N auto layout  <declarations>` means that group has Figma's auto layout. Bake it like this:

1. Bake each layer's own lines first. They carry no move; the layout places them. A `translate: none` there means the code gives that layer a translate: take it off, or it would land on top of where the flex puts it.
2. Check the rules that reach the layers through their parent or siblings, as for a plain group above. Then wrap the layers in one new element (a `div` unless the content calls for another tag), placed where the first of them sits in the markup, holding them in the order the `group N` line lists them (their order in the code). Name it for what it holds, in the page's naming style, and give that name when you list what you touched. finetune only offers auto layout on layers that share a parent; if they don't, stop and ask.
3. Give the new element the line's declarations, except `translate`. Its `margin-*` are the layers' outer margins, which it takes over (step 6).
4. If the layers were placed with `position: absolute` and `left` / `top`, the new element takes `position: absolute` and `left` / `top` set to the smallest `left` and `top` of the layers the layout places (not one on its own `group N <selector>` line), plus the line's `translate` folded in. Take `position`, `left`, `top`, `right`, `bottom` and `inset` off the layers, and nothing else. When they come from a class other elements share (like `.hl-block`), don't edit the shared rule. If the class sets nothing but those, take it off the layers. If it sets anything else (`.hl-block` also sets `white-space: nowrap`), keep it and give the layers `position: static` (its `left` / `top` then do nothing), or split the class; say which you did. If the layers were in normal flow, the new element sits in flow, and a `translate` stays as its `translate`.
5. A `group N <selector>  <declarations>` line is that layer's CSS inside the new element; bake it after the layer's own line (it wins where both set a property). One with `position: absolute; left; top` is a layer with Ignore auto layout: it stays inside the new element with those values (they're relative to it, and place its margin box as `left` / `top` do), and the new element gets `position: relative` unless it already has a position.
6. Flex adds every margin and collapses none, so the `group N <selector>` lines set the layers' margins to 0 (the gap holds the space between them) and the new element's line carries the outer ones. A `width` / `height` in px there is a layer that filled its old parent, or one ignoring the layout that would otherwise shrink to fit: it keeps that size. That size is the one at the header's width: where the layer's code made it fill, ask before freezing it (see step 2 of "Bake the changes list"). Take off no other margins and add no other sizes.

How Copy writes it: Copy lists a group's auto layout after the group's line (which then names the layers in the code's order): `group N auto layout  display: flex; flex-direction: column; row-gap: 8px; justify-content: flex-start; align-items: flex-start; width: fit-content`, the padding longhands, then the layers' outer margins (the first's start and the last's end along the flow, the smallest across it) before `width` when not 0, and `translate: X Y` last when she moved the group as a whole. Then a `group N <selector>` line for each layer that needs one, in the code's order: `margin-*: 0px` for every margin a placed layer has (the preview places border boxes; flex adds margins and collapses none, so the gap holds the space and the new element the outer margins), a px `width` / `height` for a layer whose size filled its old parent (in a hugging flex it would shrink to its content), and for an ignored layer `position: absolute; left; top`, measured from the frame to its margin box, plus its px `width` unless that's fixed (out of the flow it would shrink to fit). The layers' own lines carry no move; a layer whose code gives it a translate gets `translate: none`, so the code's doesn't land on top of the layout (its translate is taken over as a move while the layout shows it).

### Deletes

`<selector>  delete` means she deleted that layer (Delete or Backspace). Remove the element from the code, and anything that only styled or fed it. If it's rendered by a loop, a shared component or data used elsewhere, say what else would go and ask first.

### Ungroups

`<selector>  ungroup` means she ungrouped that container (⇧⌘G on a layer that holds others, Figma's Ungroup). Remove the wrapper element from the code and keep its children where it was, in the same order, so they become children of its parent. On the live page the wrapper only stopped drawing a box (`display: contents`), which is how the page lays out with it gone, so the children's own lines (a `translate`, a `width` or `height`) were measured that way: bake them as they come, after the unwrap. Where a child's move only stands in for the wrapper's own placement (its `position` with `left` / `top`, its margins, its place in a flex or grid), fold it in: give the children that placement the way the wrapper had it and drop the move, as long as nothing moves on screen. Then, as for a group, find the rules that reached the children through the wrapper (`.wrapper > .child`, `.wrapper .child`, `:nth-child()` counted among its children, `:has()` on it) and re-point each so it matches exactly what it matched before, or ask. A child's selector in Copy may run through the wrapper's path; find the element, not the path.

The ungroup also kept everything around the wrapper where it was, so Copy can carry lines for its neighbours: a `translate` on the other children of its parent, a fixed `width` / `height` (with `flex-shrink: 0` in a flex row) on them or on its own children, and a size on the parent. They only stand in for the reflow the unwrap causes. In plain flow (the wrapper's padding or margins went), fold them in the same way: put the space back where it came from (a margin or gap on the children) and drop the moves, as long as nothing moves on screen. In a grid or a flex row, the children become the parent's own items in the code and take cells or slots of their own, which moves the layers after them: say so and ask whether to lay the children out in the code (a span, a nested grid, the wrapper's track given to one child) or bake the moves as they come.

The children still inherit from the wrapper on the live page (`display: contents` keeps it in the DOM), and in the code they won't. Before taking it out, list every inherited property it sets, from its rules, its classes (Tailwind utilities such as `whitespace-nowrap` or `text-white` included), its inline style and her edits on it: `white-space`, `color`, `font-*`, `line-height`, `letter-spacing`, `word-spacing`, `text-align`, `text-indent`, `text-transform`, `text-shadow`, `visibility`, `cursor`, `direction`, `writing-mode`, `list-style`, and CSS custom properties. Copy's `<selector>  carry to children: …` line lists the ones it saw live (her edits on the wrapper, and inherited values it sets that its parent doesn't and a child still reads); custom properties from the code aren't on it, so check those in the code. Move each onto the children (or onto a class they share) so they compute exactly as before, or ask. A child that sets its own value doesn't need it.

First check what the wrapper carried of its own, since that goes with it: a fill, border, padding, shadow, rounded corners, opacity, a transform, a clip, a filter, a `::before` / `::after`, an event handler, a `role` or `aria-*`, an inherited property its children read (above) that can't simply move onto them, or a tag that means something (`button`, `label`, `li`, `td` / `th`, `form`, `fieldset`, `summary` / `details`, a heading, `section` / `nav` / `article`). If it carried any of these, or it's a component (or rendered by one), say what would be lost (its look, or for a tag its meaning and behaviour: a submit, a label's focus, valid list or table markup) and ask first. A link is never listed: finetune refuses to ungroup one.

### Images

`src: new image "name"` means she picked a different image from her computer. Ask where that file lives (or where to put it), then point the `src` at it.

### Strokes, shadows, blurs and hidden fills

`outline` / `outline-offset` are a Stroke (an outline, so it never moves the layout; Inside is a negative offset). `box-shadow` is the Drop and Inner shadows, `filter: blur()` is Layer blur and `backdrop-filter` is Background blur (written as `-webkit-backdrop-filter` first, then `backdrop-filter`; keep that order). On a box, `filter` also carries its Adjustments. A `filter` or `backdrop-filter` also lists the page's own other functions (a glass's `saturate()`, a `grayscale()`, a `url()`) as the browser resolved them: keep the code's own form for those (its `var()`s), and change only the `blur()`, `drop-shadow()` and adjustment functions. `none` means she removed something the page had. `background-color: transparent` (or `color` / `fill: transparent`) is a fill she hid.

### Clip content

`overflow: hidden` / `visible` on a container is Clip content (Figma's checkbox). Clip content is only on a real container; a group's auto layout has none until it's in the code.

### Corners and blend

`border-radius` (or `border-top-left-radius` and the other longhands, for independent corners) is Corner radius. `corner-shape: superellipse(k)` came with Corner smoothing, and its radii are already scaled for it; if the project's rules limit squircles or superellipse corners to some components, check before baking it elsewhere and ask. `mix-blend-mode` is the Blend mode row (`normal` over the code's own mode means she set it back to Normal).

### Auto layout on a container

Auto layout on a container is its own CSS, written as longhands. Like every line, it lists only what changed: a gap or alignment without `display` means the code already makes that container flex or grid (as `div.card` in the sample). If the code doesn't, it changed since Copy: list the line and ask, don't add the flex yourself.

- **Flow:** `display: flex` (`inline-flex` on an inline element) + `flex-direction` (`column` Vertical, `row` Horizontal). `display: block` / `inline-block` is Freeform where the code had flex.
- **Wrap:** `flex-wrap: wrap`.
- **Gap:** `row-gap` or `column-gap`. A grid or a wrapped row has two gap fields, Horizontal and Vertical, so its line carries only the one she changed (on a `gap-6` grid, `row-gap: 32px` alone is `gap-x-6 gap-y-8`). `justify-content: space-between` is Gap Auto.
- **Alignment** (the nine dots): `justify-content` along the flow + `align-items` across it. With Wrap, `align-content` comes with `align-items` (the same side): it packs the rows, so the Vertical gap is the space between them. When the code's `align-items` was `stretch` or `normal`, finetune adds `align-self: stretch` to the children that filled across, so they keep filling.
- **Padding:** `padding-top`, `padding-right`, `padding-bottom`, `padding-left`. Write them as the code writes padding (the shorthand is fine in the code).
- **Margins of 0** (`margin-top` / `margin-bottom`, or `-left` / `-right`) on the children of a container she turned into auto layout: the margins between them made the space she saw (block margins that collapse, or margins in a row), and the gap holds that space instead, as Figma's does, so bake both together. A `margin-top` / `margin-bottom` on the container itself, with 0 on its first or last child, is a child's margin that collapsed out through it: flex would hold it inside and grow the container, so it moves onto the container.
- **Hug:** `width: fit-content` / `height: fit-content` (written only when the code's own size doesn't already hug).
- **Fill along the flow:** `flex-grow: 1; flex-basis: 0px; min-width: 0px` (`min-height` in a column). When the container hugs along the flow, finetune first makes it Fixed (a px size on the container, with the lines below), as Figma does, or the layer would grow from nothing into nothing. **Fill across:** `align-self: stretch` (`justify-self` for a grid's width), with `width: auto` / `height: auto` when the code sets a size that would stop the stretch.
- **Fixed:** `width` / `height` in px, with `flex-grow: 0; flex-shrink: 0; flex-basis: auto` along the flow, and `align-self: flex-start` across it when it had been stretching (`start` in a grid, and `justify-self` for a grid's width).
- **Ignore auto layout:** `position: absolute` + `left` / `top` on the child, with `position: relative` on the container when the code left it static. The container stays static when making it relative would move another absolute layer inside it; then `left` / `top` are measured from the box the layer already sits in. Turning it off takes finetune's `position`, `left` and `top` away, so the code's own (a `relative` included) stand. `position: static` is written only where the code itself makes the layer absolute or fixed: bake it as written (the code's `left` / `top` then do nothing).

Spacing on a container that isn't flex or grid comes as `translate` moves of its children, baked like any move.

### Size

`width` / `height` from a resize are the CSS size (padding and border already taken off for `content-box`). Inside auto layout, a resized layer is Fixed, so its `flex-*` lines come with it.

A resize (a typed W or H, Make selected N cols wide, a handle drag) changes one axis at a time, so it can write values she didn't type. Each comes with a comment line after the layer's own line, `/* <selector>: <property>: <value> <why> */`, and Copy prints it only while the layer still has that value. Bake the value with the rest of the line; the comment is for you, not the code.

- **A pinned axis** (`width: 692px kept: only the height was changed, and the code's aspect ratio would have changed this too`): the code makes this axis follow the other (an `aspect-ratio`, or an image's own ratio with this axis auto), so it's written as px to hold it where it was (to two decimals, the size it had). Bake it as a fixed size on that element. If the element's width comes from a fluid rule in the code (a grid column, `width: 100%`), say that the px makes it fixed and ask whether she'd rather keep it fluid and drop the `aspect-ratio` instead.
- **`object-fit: cover` added**: an `<img>` or `<video>` changed shape and the code gave it no `object-fit` (the default `fill` stretches it), so cover, Figma's default image fill, crops it instead. Only a box that truly changed shape gets it: an image with `height: auto` that just got wider keeps its ratio and gets neither this nor a height. Bake it on that element's rule. An `object-fit: fill` the code writes itself is never replaced, so this note means the code had none.
- **`align-self: start` added** (`flex-start` in a flex): the layer's grid or flex row stretched it to the row's height, so after the width change it couldn't wrap its content. Bake it on that element; it's what lets its height follow what's inside it.

A width change also writes sizes inside the layer that followed it: a child that filled the old width of a parent whose width is set (the layer itself, or a parent with a width in the code) gets the new one, even one as wide as its own content (a `width: 400px` wrapper round a 400px image), and an image, video or `<svg>` with a px height gets the height that keeps its proportions. They're ordinary `width` / `height` lines on those children; bake them as sizes. Text size, line height, stroke and radius are never in them.

A K scale's `width` / `height` follow the same rules: only an axis that was Fixed gets a size (Hug and Fill follow on their own and get none), and inside auto layout its `flex-*` lines come with it.

### Scale

A `/* <selector> scaled <f>x (K) */` comment line says she scaled that layer, and everything inside it, by f with Figma's Scale tool (K), counted from the code's own values. The lines after it are ordinary declarations, already multiplied: bake them like any other line. The comment comes before the lines of every layer inside that layer, and heads only those. A layer scaled inside another scaled layer comes after the outer layer's own lines, and its comment also gives the factor its values carry (`/* #ttl scaled 1.5x (K), 3x with #card's */`): that whole factor is the f for the token check on the lines under it.

- Where the code's value is a single length written as a `var()`, a `rem` or a `clamp()`, write `calc(<the code's value> * f)` instead of the px on the line (`calc(var(--space-3) * 1.5)`), but only when the code's value times f comes to the line's px (within 0.01px plus 0.00005 of the value, as f is given to 8 digits). It's exact on that element, keeps the token, and keeps a `clamp()` responsive. Never put a raw px over a token without saying so.
- Never wrap a list in `calc()`: a shadow, a filter, a `clip-path` or `shape-outside` shape, a gradient, grid tracks, `background-size` / `-position`, `border-spacing`. `calc(var(--shadow) * 2)` is invalid, so the shadow or clip is lost, and a list holding `rem` is thrown out whole. Where such a value is a `var()` or holds `rem`, put the `calc()` on each length inside it (`0 calc(0.25rem * 2) calc(0.5rem * 2) rgba(0, 0, 0, .2)`), and only where the token is the list's own (one `var()` for the whole shadow can't be multiplied inside): otherwise bake the px value given and tell her it replaces the token.
- When it doesn't come to the line's px, the scale started from an edit she made before pressing K (Typography's size, say), not from the code's value: bake the px as given and tell her that line replaces the token.
- An `em` value that followed its font size (the font size grew) gets no line: leave the code's `em` as it is. So a line on a value the code wrote in `em` means the em did NOT follow: that element's font size wasn't scaled (a box with no words in it keeps its font size), and the code's em would give the old size. Bake the px given, or `calc(<em value> * f)` (`calc(5em * 2)`), which is exact on that element when it comes to the line's px as above. Never `calc()` an em that has no line: that would multiply it twice. A `%` that gets a line: bake the px given.
- Border, outline and column-rule widths, `outline-offset` and `border-spacing`: write the number as given (1.5px), even if the screen shows it rounded (Chrome draws them on whole device pixels). One the code wrote in `em` follows the font size and gets no line where its font size grew (else the em rule above). `border-spacing` is inherited, so it gets a line only on the element that sets it.
- A `/* <selector>::before: <properties> not scaled (K) */` (or `::after`) line names px lengths of that pseudo-element which stayed while the layer around it grew: finetune can't write to a pseudo-element. Multiply them by f in its rule (for a token, `calc()` as above), or list them for her and ask if the rule is shared with layers she didn't scale.
- When a second K brings the whole factor back to 1, the values that come out as the code's own have no line and there's no comment: nothing is left to bake for them.
- A `font-size` line on an `<svg>` that holds words (`<text>`, or HTML in a `<foreignObject>`) keeps its words from scaling twice: the svg's viewBox already scales them, so it holds the svg at the font size it had. Bake it on that `<svg>`.
- A shape's `scale` keeps 4 decimals on purpose (`scale: 1.3333`): it multiplies the whole drawing, so 2 decimals would be off by a visible amount on a big shape. Bake it as given.
- `attribute viewBox: "0 0 w h"` is an attribute, not CSS: add `viewBox="0 0 w h"` to that `<svg>` in the markup (or the component's prop for it). It had none, and without one its drawing wouldn't scale with its new size.
- A `/* <selector>: animated <properties> not scaled (K) */` line names values an animation or transition held, which the scale left as they were. List them for her and ask; never multiply keyframes on your own.
- A shape's `scale` with `transform-box` / `transform-origin` follows the SVG rule below; its stroke scales with it. A shape drawn with `vector-effect: non-scaling-stroke` keeps it and gets multiplied `stroke-width`, `stroke-dasharray` and `stroke-dashoffset` lines instead (non-scaling strokes and dashes are in screen px, which the `scale` doesn't reach).
- A selected rect's `rx` / `ry` lines are its corner radius, multiplied; a rect, circle or ellipse also gets its stroke's width and dashes multiplied (its new geometry doesn't reach them).

### SVG and icons

On an SVG shape, `fill`, `stroke`, `stroke-width`, `r`, `rx`, `ry` and a rect's `width` / `height` are its own paint and geometry: write them as CSS on that shape, or change the matching attribute where the SVG is inline markup. `translate` inside an SVG is in its user units, not screen px. `transform-box: fill-box` + `transform-origin: center` came with a rotate, flip or resize (keep them while any of those stays); `vector-effect: non-scaling-stroke` came with a `scale` resize. A K scale keeps a shape's `vector-effect: non-scaling-stroke` (on the shape it's on, or inside a scaled `<svg>`) and multiplies its `stroke-width` and dashes instead, so the stroke comes out f times as thick, as Figma's does, whatever the svg's viewBox. `filter: drop-shadow()` is its Drop shadow (on an `<svg>` too, so it follows the drawing). `color` on an `<svg>` is an icon's color (its shapes paint with currentColor): write it where the icon gets its color (a class, or the component's `color` prop). `stroke-width` on an `<svg>` is a line icon's weight, unitless in its own units (Lucide's `strokeWidth` prop); on the icon's shapes it's the same weight where each shape sets its own (change each `stroke-width` attribute).

A `<selector> svg` line is the SVG filter that element's `filter: url(#ft-tone-…)` points at (image Temperature, Tint, Highlights, Shadows). Put that `<filter>` in one hidden `<svg width="0" height="0" style="position:absolute">` in the page, never `display: none` (that turns filters off).

### Components

`component <Name> (<element>, N on the page)` is a change to the component itself, so every instance changes (an edit on a selected instance reaches every instance, as in Figma, until she presses Override, which makes its edits that instance's own): write it where the component styles the element it renders (its CSS rule or class, in the component's file or the stylesheet it uses), never at a place it's used. `<selector> (this <Name> only)` is one instance's own change (an Override, a move, its words): write it where that instance is used in the code (a class or style passed to it, or a modifier class on it), not in the component. `<selector> (inside this <Name> only)` is a layer inside one instance of a component that's on the page more than once: it changed on that instance only, so write it the same way (through what that instance is given), never into the rule the component styles it with, which every instance shares. If the component doesn't pass a class or style through to its element, say so and ask before changing the component. With an `@` (see "The changes list"), a `component` line's file is the component's own and an instance line's is where that instance is used; an `inside this` line names both.

A component in `components/ui/` (shadcn's primitives, in Lovable's apps and most others) is shared by the whole app, so `N on the page` counts this page only, not who else the edit reaches. Before changing one there, search `src/` for its imports, list the pages and components that use it, and ask. The other way is the `className` at this page's call sites, baked as a `(this X only)` line for each.

`component <Name> variant=<v>` is one variant's change: on the page it reached only the instances given that variant. Where the component builds its classes with cva (shadcn's `buttonVariants`), write colour, border and shadow changes into that variant's entry, never the base string, which every variant shares. A change to size (padding, height, font size) belongs to cva's `size` entries, which every variant shares: say so and ask.

The page can't read the cva's `defaultVariants`. `variant=(none)` is the instances given no variant: write it into the entry `defaultVariants` names. If any instance in the code passes that entry's name explicitly (`variant="primary"` where `defaultVariants` is `primary`), the edit reaches it in the code too, though the page kept it apart: say so and ask. `variant=default` on instances given none is read that way because another instance passes `default` by name (shadcn's naming); if the cva's `defaultVariants` names another entry, say so and ask.

A `component <Name>` line with no `variant=` on a cva component:
- With no `; variants` part, no instance on the page passed a variant, so every one was the `defaultVariants` entry: write it there, as for `variant=(none)`. Writing it into the base string would change every variant in the app.
- With `; variants a, b` (a save from before variants were told apart), it reached those variants on the page. Write a property that the variant entries set (colour, border, shadow) into each listed entry; in the base string it would lose to them. Or ask.
- With `; intents` or `; tones` and no variants, the cva keys its colours by that prop instead: ask which entry holds the property.

cva joins its classes in this order: the base string, the variant's entry, the size entry (and any `compoundVariants` that match), then the `className` each instance is given. `cn`'s tailwind-merge keeps the last class for a property. So before writing into an entry, check each size listed on the line (shadcn's `sm` and `lg` entries carry `rounded-md`) and each instance's `className`, at its use site or in the outer component that renders it (`<Card className="shadow-elegant">`), for a class on the same property. Where one sets it, the edit won't reach those instances in the code, though the page showed it on them: write it there too, or ask.

`; k inside <Outer>` means k of the instances are rendered by another component that returns this one; they changed on the page too, and the edit in this component's file reaches them, unless the `className` that `<Outer>` passes sets the same property (see above). Where an `<Outer>` line sets the same property, or a shorthand of it (`border-radius` over this line's `border-top-left-radius`), its value holds on those k, as the outer component's class passed in does in the code.

### Motion

`animation-name`, `animation-duration`, `-delay`, `-timing-function`, `-iteration-count`, `-direction` and `-fill-mode` are lists, one value per animation in the element's `animation-name` order. Write each into the rule's `animation` shorthand or longhands, whichever the code uses, matched by name.

An `animate() <properties>` line is a JavaScript animation (`element.animate()`) she tuned in Motion: "on <selector> and N more, called from <function>()" says where it runs, then each change as was → now (duration, delay, easing, iterations, direction, fill; "delay per layer" is a stagger, in the order the layers start; "keyframe N" is that keyframe's value). Find the `.animate(` call in the source (the function named, the keyframes shown as "was") and change its options and keyframes there. A stagger written as a formula (`delay: i * 50`) changes its step. If you can't find the call, list the line and ask.

A `@keyframes <name> (new)` line is an animation she added from Motion's generic list (Dissolve, Slide in...): add that `@keyframes` to the stylesheet the element's rule lives in, as given (its body is the keyframes, her changes included). The element lines that run it carry its `animation-*`.

A `@keyframes <name> <key>` line (`@keyframes hl-rise 0%`) is a keyframe she changed in Motion (its direction, distance, scale, rotation or opacity): write those declarations into that keyframe of that `@keyframes` (`0%` is `from`, `100%` is `to`), where the code defines it. Every layer using those keyframes changes with it; if another page or component uses them too, name it and ask first.
